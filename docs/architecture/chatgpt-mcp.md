# Подключение CRM 3.0 к ChatGPT через MCP

CRM публикует приватный MCP-сервер по адресу `https://zoom78.com/mcp`.
ChatGPT подключается к нему через экран «Создать MCP-приложение» с OAuth.
Архив плагина и OpenAI API key для этого подключения не требуются.
Доступ к существующим платным AI-функциям CRM использует её текущую конфигурацию Polza.

## Устройство

- Django обслуживает вход, согласие OAuth, выдачу и отзыв токенов, discovery metadata и выдачу файлов.
- Сервис Compose `mcp` использует тот же backend image, PostgreSQL и media volume. Он запускает
  `python -m uvicorn apps.mcp_connector.server:application --host 0.0.0.0 --port 8001 --no-access-log`.
  Порт `8001` не публикуется на хосте. Обычный backend продолжает работать через Gunicorn.
- Для MCP переопределён entrypoint: запуск не повторяет миграции, создание суперпользователя и сборку статики.
- Nginx направляет `/mcp` в MCP-процесс, а `/oauth/`, `/.well-known/oauth-*` и `/mcp-files/` — в Django.
  Эти маршруты доступны только по HTTPS; HTTP-входы на портах 80 и 8000 отвечают `403`.
- Streamable HTTP работает без состояния транспортной сессии. Длительные операции возвращают сохранённое задание.

Конфигурация backend и MCP-процесса должна совпадать:

```dotenv
MCP_PUBLIC_URL=https://zoom78.com/mcp
MCP_OAUTH_ISSUER=https://zoom78.com
MCP_FILE_DOWNLOAD_HOSTS=oaiusercontent.com
```

Значения входят в `.env.production.example`; реальные настройки остаются в серверном `.env.production`.
`MCP_PUBLIC_URL` — точный идентификатор OAuth resource, без завершающего `/`.
Nginx сохраняет исходные Host и схему запроса. Для другого домена нужно согласованно изменить
эти значения, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, сертификат и конфигурацию reverse proxy.
При `DEBUG=False` cookies сессии и CSRF имеют флаг `Secure`: вход в Django admin и OAuth
требует HTTPS. Для локальной отладки входа по HTTP нужен `DEBUG=True`; локальный reverse proxy
при этом продолжает блокировать MCP/OAuth по HTTP.

## Первоначальная настройка

Развёртывание выполняется через существующий CI/CD после согласования доступа к production.
Backend применяет стандартные миграции Django до старта MCP. На этапе проверки изменения
не предоставляют доступ ни одному пользователю автоматически.

После миграций администратор явно разрешает подключение существующей учётной записи:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production exec backend \
  python manage.py grant_mcp_access --username Vova
```

Команда находит пользователя и сохраняет разрешение по его ID. Переименование пользователя
не передаёт доступ другому аккаунту. Позднее таким же способом можно разрешить отдельного сотрудника.
Разрешение и scopes можно просматривать и изменять в Django admin.

Зарегистрируйте OAuth-клиент с точным redirect URI, показанным ChatGPT в настройках MCP-приложения:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production exec backend \
  python manage.py configure_mcp_client \
  --name ChatGPT --redirect-uri 'ТОЧНЫЙ_HTTPS_CALLBACK_ИЗ_CHATGPT'
```

Новый `client_id` и `client_secret` выдаются для ручного ввода в расширенные настройки OAuth ChatGPT.
Не добавляйте их в Git, описание приложения, промпты или общие журналы. При необходимости
перевыпуска используется `--rotate-secret`; повторный показ действующего секрета не предусмотрен.
Callback разрешается точным совпадением, без wildcard. Используется Authorization Code с PKCE S256,
обновлением и отзывом токенов; клиентские пароли не передаются модели.

Discovery endpoints:

- `https://zoom78.com/.well-known/oauth-authorization-server`
- `https://zoom78.com/.well-known/oauth-protected-resource/mcp`
- `https://zoom78.com/.well-known/oauth-protected-resource` — совместимый alias того же resource.

## Подключение в ChatGPT

1. Откройте «Новый плагин» → «Создать MCP-приложение».
2. Назовите подключение, например `CRM 3.0`.
3. Введите URL `https://zoom78.com/mcp`, выберите **OAuth**.
4. Проверьте обнаруженные настройки и внесите client ID/secret в расширенные настройки OAuth.
5. Проверьте предупреждение и создайте подключение. Установите созданный плагин, если интерфейс предлагает это отдельно.
6. Подключите аккаунт: откроется страница CRM. Войдите под `Vova` и подтвердите запрошенные scopes.
7. Выберите CRM через `@` в чате и выполните проверочные запросы ниже.

Названия пунктов могут отличаться между версиями интерфейса ChatGPT. Настройка OAuth и поведение
подтверждений описаны в [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/custom-mcp-server).

## Возможности и права

Каждая операция представлена отдельным инструментом с именем, параметрами и аннотациями.
Произвольных URL, HTTP-методов, SQL и административных операций через MCP нет.
Вызовы выполняются от имени пользователя OAuth с сохранением авторства и канала `ChatGPT`.

| Область | Возможности |
| --- | --- |
| Клиенты и сделки | Поиск, карточки, создание и изменение, история, закрытие, восстановление, дубли и объединение. |
| Работа со сделкой | Задачи, исполнители, сроки, чеклисты, заметки, сообщения и уведомления. |
| Страхование | Полисы, предложения, участники, документы, транспорт, ипотека, заявки и их версии. |
| Финансы | Платежи, финансовые записи, ведомости, статусы, сводки и поддерживаемые экспорты. Это учёт CRM, а не банковские переводы. |
| Файлы | Каталог, текст и страницы, загрузка вложений ChatGPT, скачивание и поддерживаемые операции с файлами. |
| Почта | Адрес и создание ящика сделки, чтение писем и явный запуск импорта. Отправка писем не добавлена. |
| AI | Библиотека, личные чаты, запросы и состояние заданий. Платные операции выполняются отдельной явной командой. |

Scopes `crm.read`, `crm.write`, `crm.destructive`, `crm.files`, `crm.mail`, `crm.ai` ограничивают
разрешённые инструменты, но не заменяют права конкретного пользователя на объекты CRM.
Каждый вызов перепроверяет активность аккаунта, разрешение подключения и действующие права.
Если ChatGPT не указал scopes, экран согласия предлагает разрешённые этому пользователю
возможности. Явно запрошенный более узкий набор сохраняется; ограничение пользователя не расширяется.
Обычные ключи Codex не используются и остаются отдельным каналом интеграции.

Действующие права разделов различаются. В частности, каталог клиентов в CRM общий для вошедших
пользователей: подключение сотрудника не создаёт новую изоляцию клиентов «только по своим сделкам».
Перед включением новых сотрудников проверьте их доступ и связи на тестовых данных.

Через MCP не предоставляются управление пользователями, ролями, паролями, настройками интеграций
и произвольными почтовыми ящиками. Старый MVP оформления Сбера, интерфейс которого удалён,
в реестр инструментов не входит.

## Предпросмотр и повторные запросы

Удаление, объединение, перенос, финансовые изменения, изменение доступа, замена важных реквизитов
и массовые операции требуют предпросмотра. Он показывает точные изменения и зависимости,
не создаёт папки, заметки или внешние задания. Подписанный токен действует 30 минут и связан
с пользователем, OAuth-клиентом, операцией, параметрами и исходным состоянием.

Применение повторно проверяет права и актуальность. Изменённые исходные данные требуют нового
предпросмотра. Записи защищены UUID идемпотентности: точный повтор возвращает сохранённый результат,
а другое тело с тем же UUID отклоняется. Не повторяйте внешний вызов с новым UUID, если его
результат ещё неизвестен; сначала проверьте состояние исходного запроса или задания.

Подтверждение человеком обеспечивает интерфейс ChatGPT. Аннотации инструментов и предпросмотр
не являются отдельным серверным доказательством клика человека. Пользовательские настройки
ChatGPT могут запрашивать подтверждение также для обычных записей.

## Импорт полиса, платёж премии и комиссия

Для импорта документа используйте `crm_create_policy_draft`: он создаёт новый полис,
платежи страховой премии, финансовые записи и план переноса оригиналов. Распознавание
через `crm_recognize_policy` само по себе не сохраняет полис и не перемещает документы.
Обычный `crm_create_policies` создаёт только карточку полиса и не заменяет этот сценарий.

Передайте все исходные документы в `arguments.data.source_file_ids` специализированного
инструмента. Принимаются Drive ID, возвращённые распознаванием, и непрозрачные MCP ID вида
`d_...` из доступного каталога файлов сделки. Это не URL и не содержимое файла.
Другие инструменты записи не принимают произвольные `source_file_ids`.
Все источники проверяются до сохранения: они должны принадлежать выбранной сделке,
быть доступными пользователю и находиться вне корзины и папок других, в том числе удалённых,
полисов. Чужие папки полисов и shortcuts не обходятся.
Для безопасного восстановления после сбоя требуется контрольная сумма Drive исходного
загруженного файла: поддерживаются обычные PDF, изображения и документы Office.
Нативные Google Docs/Sheets и shortcuts не импортируются. Такой источник сначала вручную
экспортируют в обычный файл поддерживаемого формата и загружают в выбранную сделку.

Пример запроса предпросмотра:

```json
{
  "tool_name": "crm_create_policy_draft",
  "arguments": {
    "data": {
      "deal": "UUID_СДЕЛКИ",
      "number": "НОМЕР_НОВОГО_ПОЛИСА",
      "insurance_company": "UUID_СТРАХОВОЙ",
      "insurance_type": "UUID_ВИДА_СТРАХОВАНИЯ",
      "payments": [{"amount": "15000.00", "actual_date": "2026-10-25"}],
      "source_file_ids": ["d_ID_ИЗ_КАТАЛОГА"]
    }
  }
}
```

Для каждого нового платежа пустой или отсутствующий массив `incomes` заполняется одной
неоплаченной записью на `1.00` рубля с пустыми описанием и источником. Примечание —
`Комиссионное вознаграждение от <название канала продаж>`, а без канала —
`Комиссионное вознаграждение`. Дата финансовой записи остаётся `null`.

Пустой или отсутствующий массив `expenses` получает неоплаченные записи на `1.00` рубля:
сначала контрагенту, затем исполнителю. В базе расход нормализуется в `-1.00`.
Контрагент выбирается в таком порядке: явно переданное непустое `counterparty`, клиент
сделки с признаком `is_counterparty`, действующий неудалённый `referred_by` клиента сделки.
Примечания имеют вид `Расход контрагенту <имя>` и `Расход исполнителю <полное имя>`,
для исполнителя без полного имени используется username. Если соответствующего получателя
нет, запись для него не создаётся. Страхователь полиса не заменяет клиента сделки в этом выборе.

Непустые явно переданные массивы доходов и расходов сохраняются, включая суммы `0.00`,
даты и примечания. Автозаполнение каждой стороны независимо от другой. Эти правила действуют
только при создании через MCP; `crm_update_policy_draft` и обычный HTTP API их не применяют.
Подготовленные суммы, даты и все записи видны в `changes.requested` до подтверждения.

`payments[].actual_date` означает оплату страховой премии. Она не заполняет даты комиссии
и расходов и не создаёт доход в размере премии. `paid_balance` складывается из финансовых
записей с заполненной датой и не является признаком оплаты премии. Записи на один рубль
служат неоплаченными заготовками для последующего уточнения.

После подтверждения полис и его финансовый граф сохраняются атомарно. Оригиналы файлов
перемещаются в папку нового полиса после фиксации данных. Вложения заметок отвязываются
только после подтверждённого переноса соответствующего файла. Переносы не копируют документы
и не изменяют ранее существовавшие полисы. При совпадении номера действующего полиса
импорт не дополняет его автоматически.

В `data.file_transfer` возвращается явное состояние, например:

```json
{
  "status": "files_pending",
  "files": [
    {"file_id": "d_ID_ИЗ_КАТАЛОГА", "name": "Полис.pdf", "status": "pending"}
  ],
  "error": {"code": "drive_unavailable", "retry_with_same_request_id": true}
}
```

`completed` означает завершённый перенос, а `files_pending` — что полис и финансы уже
сохранены, но работа с документами не закончена. В элементах `files` возвращаются
`file_id`, `name`, `status` (`pending` или `moved`) и, при наличии, `error`.
Без исходных файлов результат сразу содержит `{"status":"completed","files":[]}`;
создание папки в Drive для такого вызова не требуется.

При `files_pending` повторите **тот же вызов `crm_apply_change` с теми же аргументами
и тем же `request_id`**. Повтор продолжает проверку и перенос файлов после перезапуска
процесса, сохраняя уже созданные ID и финансовые записи. Новый UUID или повторное создание
полиса для продолжения не используются. Прогресс хранится во внутреннем manifest в
существующем результате `McpMutation`, не выдаётся модели и не требует новой схемы БД.
Папка назначения фиксируется отдельной сохранённой контрольной точкой до первого переноса.
До завершения возвращается частичный результат, а не утверждение об успешном импорте.

Атомарность относится к данным CRM. Для смены родителя в Drive v3 здесь нет подтверждённого
атомарного compare-and-set: metadata проверяются на предпросмотре, при применении,
непосредственно перед изменением и после переноса. Внешнее ручное изменение между запросами
Drive всё ещё возможно. Работа с файлами не является общей атомарной транзакцией с базой CRM.

## Значения инструментов и полей

`tools/list` передаёт описания назначения операций и каждого именованного входного поля,
в том числе внутри массивов платежей, доходов и расходов. Для полей сериализаторов
используются доменные пояснения MCP, затем `help_text`/подпись поля; связанные записи
описываются как CRM ID с указанием инструмента справочника. Даты имеют формат `date`
(`YYYY-MM-DD`), время — `date-time` ISO 8601, UUID — `uuid`; суммы передаются строкой
с десятичной точкой. `null` и отсутствие поля различаются: обычный PATCH сохраняет
пропущенное поле, а явное `null` передаёт пустое значение там, где оно разрешено.

| Объект и поле | Смысл |
| --- | --- |
| `Payment.amount` | Взнос страховой премии в рублях; это не доход агента. |
| `Payment.scheduled_date` | Плановый срок оплаты премии; сам по себе не подтверждает оплату. |
| `Payment.actual_date` | Фактическая оплата премии. Непустая дата означает, что взнос оплачен. |
| `Payment.paid_balance` | Производное сальдо проведённых финансовых записей: доходы со знаком плюс, расходы со знаком минус. Это не сумма оплаченной премии и не долг по ней; поле не задают вручную. |
| `FinancialRecord.amount` | Комиссия/доход или расход агента, связанный с конкретным платежом премии. В обычном создании финансовой записи положительный знак задаёт доход, отрицательный — расход. Изменение знака при редактировании сохраняет существующий тип операции. |
| `FinancialRecord.date` | Дата проведения именно комиссии или расхода. `null` означает непроведённую операцию независимо от оплаты премии. |
| `Statement.paid_at` | Дата выплаты ведомости комиссий/расходов; устанавливает даты входящих в неё финансовых записей, не изменяя оплату премии. |

Пример: при оплаченной премии `51500.00` и ещё не полученной комиссии `1.00`
платёж содержит `amount="51500.00"`, `actual_date="2026-10-26"`, а доход —
`amount="1.00"`, `date=null`. Нулевое сальдо финансовых записей в этом случае
не означает, что премия не оплачена. Создавать доход на `51500.00` для признания
премии оплаченной нельзя.

В `crm_list_payments` фильтр `paid` относится к `actual_date`. Для финансовых записей
`paid_only`/`unpaid_only` относятся к собственной `date`, а `payment_paid` — отдельно
к оплате связанной премии. В `crm_statement_apply_amount` процент вычисляется от
`abs(payment_paid_balance)`, а не от суммы страховой премии.

`crm_update_policy_draft` заменяет граф платежей и финансовых записей: пропущенные
элементы могут быть удалены с учётом ограничений CRM. Для сохранения элементов
передавайте их существующие ID и полный нужный граф. Для одиночных правок используйте
`crm_update_payments` или `crm_update_financial_records`; заготовки по рублю на
редактировании не добавляются.

Идентификаторы файлов также различаются: `crm_list_files` возвращает CRM ID для чтения
и импорта оригиналов, а `file.file_id` при загрузке — ID вложения ChatGPT вместе с
его `download_url`. Для `source_file_ids` специализированного создания полиса допустимы
как MCP `d_…`, так и исходные Drive ID из распознавания.

Описания находятся в `descriptions.py` и `finance_descriptions.py`; они не заменяют
серверные проверки прав и не изменяют бизнес-логику. `test_descriptions.py` проверяет
смысл ключевых полей и фактическую передачу метаданных через HTTP `tools/list`.
После обновления серверного процесса клиент должен заново запросить список инструментов;
уже открытый чат может продолжать использовать ранее загруженные описания.

## Файлы и конфиденциальность

Каталог и чтение содержимого проверяют владельца и принадлежность файла. Чтение не создаёт
папку Drive, заметку или платное AI-задание. Текст и страницы извлекаются существующими
локальными средствами; применяются ограничения размера и объёма ответа.

Загрузка из ChatGPT использует стандартные file params. Получение внешних файлов ограничено
доверенными HTTPS-источниками, проверкой адресов и перенаправлений, таймаутом и пределом размера.
Пользователь прикладывает файл в чат и поручает сохранить его в конкретную сделку или полис.
ChatGPT сначала находит нужную запись, затем вызывает `crm_upload_file`: `owner_type`,
`owner_id`, объект вложения `file` и отдельный UUID `request_id`. Сам файл загружается
в папку владельца на Drive (по умолчанию); `destination="local"` доступен только для сделок.
Предел загрузки — 25 MiB на файл; несколько файлов передаются отдельными вызовами.
Например: «Сохрани приложенный PDF в сделку „Тестовая сделка“ клиента Тестов Алексей».
При создании нового полиса из вложения сначала загрузите оригинал в сделку, затем
прочитайте его и передайте возвращённый CRM ID в `data.source_file_ids` инструмента
`crm_create_policy_draft`. Создание полиса перенесёт этот же оригинал в папку полиса.
Вызов загрузки сам по себе не создаёт полис и финансовые записи.
Доверенные домены задаются через `MCP_FILE_DOWNLOAD_HOSTS` (список через запятую); по умолчанию
разрешён `oaiusercontent.com`. Не добавляйте произвольные домены и внутренние адреса для обхода ошибки загрузки.
Оригинал для скачивания выдаётся по краткосрочной ссылке `/mcp-files/<ticket>/`; ссылка является
временным разрешением на конкретный файл и не предназначена для публичного распространения.
При выдаче перепроверяются активность пользователя, разрешение подключения и доступ к файлу.

Для MCP/OAuth/файловых ссылок в Nginx отключён access log, для Uvicorn — access log процесса.
В HTTPS location этих маршрутов также отключён error log: сообщения об ошибке upstream иначе
могут содержать OAuth query или signed ticket в URL. Диагностика доступности выполняется через health и состояние контейнеров.
Не включайте логирование токенов, OAuth query, тела запросов, документов и signed ticket.
Пароли созданных почтовых ящиков и технические секреты не передаются в ответы инструментов.

## Проверка и отзыв доступа

Локальные проверки backend выполняются в его виртуальном окружении:

```powershell
cd backend
.venv\Scripts\python.exe -X utf8 manage.py check --settings=config.test_settings
.venv\Scripts\python.exe -X utf8 manage.py test apps.mcp_connector apps.policies apps.finances
.venv\Scripts\python.exe -X utf8 manage.py makemigrations --check --dry-run --settings=config.test_settings
.venv\Scripts\python.exe -m black --check .
.venv\Scripts\python.exe -m isort --check-only .
.venv\Scripts\python.exe -m ruff check .
```

Из корня проекта проверяется конфигурация без реальных production-секретов:

```powershell
docker compose -f docker-compose.prod.yml --env-file .env.production.example config --quiet
backend\.venv\Scripts\python.exe -X utf8 -m unittest scripts.test_ci_quality_gate scripts.test_production_compose
```

CI включает тесты MCP в backend core, собирает общий backend image и выполняет внутри него
`scripts/check_mcp_runtime.py`: старт ASGI-процессов, health, discovery и отказ без токена.
Deploy ожидает health MCP и проверяет единый IMAGE_TAG сервисов.
Локальный HTTP prod-like proxy блокирует MCP/OAuth; полный OAuth-тест выполняйте на HTTPS-стенде.

### Ручной выпуск при недоступном CI

Если запуск CI недоступен из-за лимита, это не считается успешной проверкой. Сначала
выполните локальные backend-тесты MCP, включая `test_policy_import_finance.py` и файловые
сценарии, проверки форматирования, Django check и Compose config. Сборка Docker и проверка
Nginx требуют работающего Docker daemon. Сохраните результаты проверок вместе с выбранным коммитом.
Контекст сборки исключает вложенные `.env*`, локальные SQLite-базы, media и staticfiles.
В образ не должны попадать конфигурация и данные из рабочей копии; настройки передаются при запуске.

Следующий пример предназначен для оператора на согласованном Docker-хосте, в корне checkout
проверенного коммита. Он не является разрешением агенту подключаться к production по SSH.
При подготовке этой доработки развёртывание не выполнялось; команды ниже служат инструкцией.
Используйте существующий backup и серверный `.env.production`; его содержимое не выводите.
Создание полиса из документа использует существующие модели: дополнительных миграций поверх
уже установленного MCP-коннектора этот сценарий не требует.
Ранее созданные полисы и финансовые записи сохраняются без изменений. Ретроспективное
исправление полисов и финансов в эту процедуру не входит; команд repair здесь нет.

```bash
set -euo pipefail
export IMAGE_TAG="$(git rev-parse HEAD)"
crm_compose=(docker compose -f docker-compose.prod.yml --env-file .env.production)
"${crm_compose[@]}" config --quiet
"${crm_compose[@]}" pull qdrant
"${crm_compose[@]}" build backend frontend
docker run --rm --entrypoint python \
  -e DJANGO_SETTINGS_MODULE=config.test_settings \
  -v "${PWD}/scripts/check_mcp_runtime.py:/app/check_mcp_runtime.py:ro" \
  "crm30-backend:${IMAGE_TAG}" /app/check_mcp_runtime.py
"${crm_compose[@]}" run --rm --no-deps --entrypoint nginx nginx -t
"${crm_compose[@]}" up --pull=never --no-build -d --force-recreate \
  qdrant backend mcp telegram_bot external_job_worker ai_answer_worker ai_index_worker frontend nginx
"${crm_compose[@]}" exec backend python manage.py check
"${crm_compose[@]}" exec backend python manage.py migrate --check
"${crm_compose[@]}" exec mcp curl -fsS http://localhost:8001/health/
"${crm_compose[@]}" ps
"${crm_compose[@]}" images
curl -fsS https://zoom78.com/.well-known/oauth-authorization-server >/dev/null
curl -fsS https://zoom78.com/.well-known/oauth-protected-resource/mcp >/dev/null
test "$(curl -sS -o /dev/null -w '%{http_code}' https://zoom78.com/mcp)" = "401"
test "$(curl -sS -o /dev/null -w '%{http_code}' http://zoom78.com/mcp)" = "403"
```

Дождитесь `healthy` у backend и MCP и проверьте, что CRM-образы имеют выбранный commit tag.
Проверьте вход через OAuth и тестовую запись. Затем сохраните tag существующим инструментом:

```bash
python3 scripts/sync_prod_image_tag.py --env-file .env.production \
  --tag "${IMAGE_TAG}" --backup-dir ../crm3-image-tag-backups
```

При обновлении действующего коннектора заново выдавать пользовательский доступ или OAuth-секрет
не требуется. Первоначальная настройка выполняется отдельно по разделу выше.
Запуск импортов в реальные клиентские сделки не входит в техническую проверку развёртывания.

Сквозная приёмка в ChatGPT проводится на тестовых данных:

1. «Используй CRM 3.0: покажи мой профиль и найди тестовую сделку …».
2. «Прочитай документ … из этой сделки и укажи источник и страницы».
3. «Создай задачу … в тестовой сделке»; проверьте автора в CRM.
4. «Подготовь изменение …»; проверьте предпросмотр, подтвердите применение и прочитайте результат.
5. Повторите вызов с тем же UUID и убедитесь в отсутствии дубля.
6. Отзовите доступ и убедитесь, что следующий вызов отклонён.

Для приёмки импорта дополнительно используйте отдельную тестовую сделку и копии тестовых
документов. Сравните `changes.requested` со всеми платежами, доходами и расходами; после
применения проверьте авторство и `data.file_transfer.status == "completed"`.
У оплаченного платежа премии комиссия и расходы без явно переданных дат должны оставаться
неоплаченными. Повтор того же apply UUID должен сохранить ID полиса и количество финансовых
записей. Отказ Drive и продолжение `files_pending` сначала проверяются автоматическими
тестами; production Drive не отключается ради проверки. Уже существовавшие полисы и их
финансовые записи в выбранной сделке должны оставаться без изменений.

Отзыв разрешения пользователя:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production exec backend \
  python manage.py grant_mcp_access --username Vova --revoke
```

Для нового подключения потребуется снова явно разрешить доступ. Отдельный OAuth-токен можно
отозвать через `/oauth/revoke/`; отключение аккаунта CRM также прекращает доступ.
При откате сначала остановите сервис MCP и закройте публичные маршруты; не удаляйте базы и media volumes.
