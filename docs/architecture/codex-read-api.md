# Доступ Codex к данным CRM 3.0

Навык «Данные CRM 3.0» читает сделки через отдельные методы `/api/v1/codex/`. Методы записи используют другой ключ и доступны только для создания заметки или группы страховых предложений. Обычный JWT пользователя CRM для этих методов не требуется; ключи Codex не подходят для остальных методов API.

## Возможности

| Метод | Назначение |
| --- | --- |
| `GET /api/v1/codex/deals/?q=<запрос>` | Поиск по сделкам, в том числе закрытым; мягко удалённые сделки исключены. |
| `GET /api/v1/codex/deals/<uuid>/` | Основные поля сделки и список доступных разделов. |
| `GET /api/v1/codex/deals/<uuid>/passport/` | Общий паспорт расчёта: сделка, клиент, все полисы, расчёты и заметки этой сделки, а также каталог документов. |
| `GET /api/v1/codex/deals/<uuid>/sections/<section>/` | Данные одного раздела: `client`, `policies`, `quotes`, `notes`, `tasks`, `history`, `finances`, `chat` или `mailbox`. |
| `GET /api/v1/codex/deals/<uuid>/files/` | Метаданные файлов сделки, клиента, полисов и вложений заметок, включая вложенные папки Drive. |
| `GET /api/v1/codex/deals/<uuid>/files/<file_id>/download/` | Содержимое выбранного файла после проверки его принадлежности сделке. |
| `GET /api/v1/codex/deals/<uuid>/mailbox/messages/<message_id>/` | Тело выбранного письма из привязанного к сделке почтового ящика. |

Списки возвращают `count`, `next`, `previous` и `results`. Параметры `page` и `page_size` позволяют читать их по частям; размер страницы по умолчанию — 50, максимум — 100. Раздел `client` возвращает один объект. В разделах `history` и `finances` параметр `kind` выбирает `events`/`audit` и `payments`/`records` соответственно. Почтовый список содержит заголовки до 100 последних писем привязанного ящика; тело письма читается отдельно по IMAP UID. Навык загружает только разделы и документы, нужные для конкретного вопроса.

Паспорт собирается при каждом запросе и не сохраняется как запись CRM. Ответ версии `schema_version: 1` содержит `generated_at`, объекты `deal` и `client`, массивы `policies`, `quotes`, `notes`, объект `files: {status, items}` и `warnings`. Записи включают свои ID и все поля без усечения; полисы и расчёты дополнены названиями связанных справочников, включая банк ипотечного полиса. Документы представлены метаданными и `download_url`, без содержимого. Сервер не выбирает актуальный полис и не смешивает данные других сделок. Навык выбирает нужные записи для конкретного страхования, отдельно показывает отсутствующие данные и расхождения с документом или сообщением пользователя. Если Drive недоступен, паспорт возвращает остальные данные с `files.status: "unavailable"` и предупреждением; если каталог превышает свой лимит, статус будет `too_large`. Если весь JSON превышает 5 МиБ, API отвечает `413` с кодом `passport_too_large`, а навык читает разделы постранично.

## Ключ чтения

Ключ чтения имеет вид `crm3_<prefix>_<secret>` и передаётся в заголовке `Authorization: Bearer <key>` только по HTTPS. CRM хранит хеш ключа и может отозвать его по префиксу. Этот ключ не разрешает запись.

Для `/api/v1/codex/` в Nginx отключён access log: поисковый запрос может содержать имя клиента и не должен попадать в журнал URL. HTTP-входы на портах 80 и 8000 отклоняют этот путь с `403`; используйте только HTTPS. Не включайте для него подробное логирование запросов или заголовков при эксплуатации.

После развёртывания API выпустите ключ через команду Django `python manage.py codex_read_key issue --name <название>`. Сохраните показанное один раз значение через `Set-Crm3Credential.ps1` из навыка `crm3-reader`: скрипт запросит ключ в защищённом вводе и сохранит его вне репозитория с шифрованием Windows DPAPI для текущего пользователя. Не помещайте ключ в `.env`, историю команд, файлы навыка, логи или сообщения чата. Для отзыва используйте `python manage.py codex_read_key revoke --prefix <prefix>`.

## Создание заметок и расчётов

Ключ записи `crm3w_<prefix>_<secret>` действует только на два метода `POST`; ключ чтения для них не подходит. Оба метода требуют заголовок `Idempotency-Key` с UUID. Повтор того же запроса с тем же UUID возвращает прежние идентификаторы, а повтор с другим содержимым — `409`. Изменение и удаление через этот ключ запрещены.

| Метод | Тело запроса |
| --- | --- |
| `POST /api/v1/codex/write/deals/<uuid>/notes/` | `{"body":"Текст заметки"}`. |
| `POST /api/v1/codex/write/deals/<uuid>/offers/` | `platform`, `calculation_url` (HTTPS), `period_start`, `period_end`, `note` и массив `offers` до 30 элементов. Каждый элемент содержит `insurance_company`, `insurance_type`, `premium`, `sum_insured` и `status` (`preliminary` или `refined`). Для КАСКО нужны также `official_dealer` и `deductible`. |

Метод предложений в одной транзакции создаёт все расчёты и итоговую заметку, затем возвращает `note_id`, массив `quote_ids` и признак `replayed`. Премия и указанная страховая сумма должны быть положительными. `sum_insured: null` допустима только для ОСАГО. Для КАСКО `official_dealer` должен быть проверенным логическим значением, а `deductible` — проверенной неотрицательной суммой в рублях; нулевая франшиза передаётся как `0.00`, отсутствие или `null` отклоняется. У остальных видов оба поля можно опустить. Точный повтор старого запроса КАСКО без этих полей по тому же ключу идемпотентности возвращает прежние ID без создания дублей. Компания и вид страхования находятся по имени без учёта регистра; если их нет, создаются новые записи справочника. Ссылка, период, платформа и статус записываются в комментарий каждого расчёта. Метод не принимает ID чужих записей, не создаёт записи в удалённой сделке и не меняет существующие расчёты. Заметки помечаются автором `Codex`; расчёты создаются без пользовательского `seller`.

Выпускайте и отзывайте ключ командой `python manage.py codex_write_key issue --name <название>` и `python manage.py codex_write_key revoke --prefix <prefix>`. Сохраняйте его через `Set-Crm3WriteCredential.ps1` из навыка `crm3-writer` в отдельном от ключа чтения каталоге Windows DPAPI. Значение ключа показывается только при выпуске и не должно попадать в репозиторий, журнал команд или сообщения. Для записи используйте `Write-Crm3.ps1`; после ответа сверяйте возвращённые ID через API чтения.

## Работа с документами

API возвращает исходный файл размером до 25 МБ, а чтение текста PDF, сканов и фотографий выполняет Codex локально. Выбранный файл хранится во временной папке только на время ответа и затем удаляется. Методы чтения не запускают CRM-распознавание документов: оно может создавать заметки и записи истории. При ссылке на файл из другой сделки API не отдаёт его содержимое.

Вложение заметки появляется в каталоге только тогда, когда его ID подтверждён в папке сделки, клиента или полиса. Если Google Drive недоступен, файловый каталог отвечает `502`, включая случай, когда часть локальных вложений доступна: так API не выдаёт непроверенные Drive ID.

В ответе навык указывает источник каждого существенного факта: раздел и ID записи CRM либо название документа и страницу. Несовпадения между полями CRM и документами показываются отдельно, без автоматического исправления.

## Проверка и развёртывание

Backend: выполните тесты приложения `codex_reader`, `python manage.py check`, проверки форматирования и статического анализа из CI. Затем проверьте сценарий с тестовой сделкой: чтение и файлы, отказ при подмене ключей, отзыв ключа, атомарную запись предложений, повтор запроса, закрытую и удалённую сделку и отсутствие записи в чужую сделку. Навыки проверьте `quick_validate.py` и тестом клиента без рабочего ключа.

Развёртывание идёт через существующий CI. Выпуск рабочего ключа записи и пробная запись в тестовую сделку — отдельный шаг после развёртывания. Существующие данные Кусаевой не переносятся в раздел «Расчёты» задним числом.
