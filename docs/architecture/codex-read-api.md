# Доступ Codex к данным CRM 3.0

Навык «Данные CRM 3.0» читает сделки через отдельные методы `/api/v1/codex/`. Методы записи используют другой ключ: он создаёт заметки и предложения, а также подготавливает структурированные данные и заявки через обязательный предпросмотр. Обычный JWT пользователя CRM для этих методов не требуется; ключи Codex не подходят для остальных методов API.

## Возможности

### Кредит и лизинг КАСКО

Проверка версии при записи предложения использует то же сравнение снимков, что паспорт заявки: отсутствие новых полей в старом снимке эквивалентно `unknown` и пустым организациям. Реальное изменение типа собственности или организации требует новой версии; исторические снимки и связи предложений не переписываются.

Подготовка заявки принимает `ownership_type: unknown|owned|credit|leasing`, `vehicle_bank` (UUID банка) и `leasing_company` (UUID лизинговой компании). `unknown` означает отсутствие сведений; старые заявки получают это значение. Организацию можно заполнить позднее: API возвращает её отсутствие как недостающие сведения. Для других видов страхования условия КАСКО не используются.

Справочник лизинговых компаний читается через `GET /api/v1/codex/references/?kind=leasing_companies`. Ключ Codex не создаёт и не изменяет этот справочник. Изменения заявки проходят существующий подписанный предпросмотр; заполнение `unknown` считается добавлением сведений, замена известного значения требует подтверждения. Поля и названия организаций включены в новые снимки и паспорт заявки. Старые снимки не переписываются; отсутствие новых полей в них эквивалентно исходным значениям при проверке `sources_changed`.

| Метод | Назначение |
| --- | --- |
| `GET /api/v1/codex/deals/?q=<запрос>` | Поиск по сделкам, в том числе закрытым; мягко удалённые сделки исключены. |
| `GET /api/v1/codex/deals/<uuid>/` | Основные поля сделки и список доступных разделов. |
| `GET /api/v1/codex/deals/<uuid>/passport/` | Общий паспорт расчёта: сделка, клиент, все полисы, расчёты и заметки этой сделки, а также каталог документов. |
| `GET /api/v1/codex/deals/<uuid>/sections/<section>/` | Данные одного раздела: `client`, `policies`, `quotes`, `notes`, `tasks`, `history`, `finances`, `chat` или `mailbox`. |
| `GET /api/v1/codex/deals/<uuid>/files/` | Метаданные файлов сделки, клиента, полисов и вложений заметок, включая вложенные папки Drive. |
| `GET /api/v1/codex/deals/<uuid>/files/<file_id>/download/` | Содержимое выбранного файла после проверки его принадлежности сделке. |
| `GET /api/v1/codex/deals/<uuid>/mailbox/messages/<message_id>/` | Тело выбранного письма из привязанного к сделке почтового ящика. |

Списки возвращают `count`, `next`, `previous` и `results`. Параметры `page` и `page_size` позволяют читать их по частям; размер страницы по умолчанию — 50, максимум — 100. Раздел `client` возвращает один объект. В разделах `history` и `finances` параметр `kind` выбирает `events`/`audit` и `payments`/`records` соответственно. Почтовый список содержит заголовки до 100 последних писем привязанного ящика; тело письма читается отдельно по IMAP UID. Навык загружает только разделы и документы, нужные для конкретного вопроса.

Паспорт собирается при каждом запросе и не сохраняется как запись CRM. Ответ версии `schema_version: 1` содержит `generated_at`, объекты `deal` и `client`, массивы `policies`, `quotes`, `notes`, объект `files: {status, items}` и `warnings`. Записи включают свои ID и все поля без усечения; полисы и расчёты дополнены названиями связанных справочников, включая банк ипотечного полиса. Документы представлены метаданными и `download_url`, без содержимого. Сервер не выбирает актуальный полис и не смешивает данные других сделок. Навык выбирает нужные записи для конкретного страхования, отдельно показывает отсутствующие данные и расхождения с документом или сообщением пользователя. Если Drive недоступен, паспорт возвращает остальные данные с `files.status: "unavailable"` и предупреждением; если каталог превышает свой лимит, статус будет `too_large`. Если весь JSON превышает 5 МиБ, API отвечает `413` с кодом `passport_too_large`, а навык читает разделы постранично.

## Ключ чтения

Ключ чтения имеет вид `crm3_<prefix>_<secret>` и передаётся в заголовке `Authorization: Bearer <key>` только по HTTPS. CRM хранит хеш ключа и может отозвать его по префиксу. Этот ключ не разрешает запись.

Для `/api/v1/codex/` в Nginx отключён access log: поисковый запрос может содержать имя клиента и не должен попадать в журнал URL. HTTP-входы на портах 80 и 8000 отклоняют этот путь с `403`; используйте только HTTPS. Не включайте для него подробное логирование запросов или заголовков при эксплуатации.

После развёртывания API выпустите ключ через команду Django `python manage.py codex_read_key issue --name <название>`. Сохраните показанное один раз значение через `Set-Crm3Credential.ps1` из навыка `crm3-reader`: скрипт запросит ключ в защищённом вводе и сохранит его вне репозитория с шифрованием Windows DPAPI для текущего пользователя. Не помещайте ключ в `.env`, историю команд, файлы навыка, логи или сообщения чата. Для отзыва используйте `python manage.py codex_read_key revoke --prefix <prefix>`.

## Создание заметок и расчётов

Ключ записи `crm3w_<prefix>_<secret>` действует на методы создания заметок/предложений, подготовки данных и управления состоянием ниже; ключ чтения для них не подходит. Создание заметки, предложений и применение подготовки требуют заголовок `Idempotency-Key` с UUID. Повтор того же запроса с тем же UUID возвращает прежние идентификаторы, а повтор с другим содержимым — `409`. Мягкое удаление ограниченного перечня записей доступно через lifecycle; изменение структурированных данных допускается только через предпросмотр и подтверждение замен. Существующие полисы и предложения этот ключ не редактирует.

| Метод | Тело запроса |
| --- | --- |
| `POST /api/v1/codex/write/deals/<uuid>/notes/` | `{"body":"Текст заметки"}`. |
| `POST /api/v1/codex/write/deals/<uuid>/offers/` | `platform`, `calculation_url` (HTTPS), `period_start`, `period_end`, `note` и массив `offers` до 30 элементов. Каждый элемент содержит `insurance_company`, `insurance_type`, `premium`, `sum_insured` и `status` (`preliminary` или `refined`). Для КАСКО нужны также `official_dealer` и `deductible`. |

Метод предложений в одной транзакции создаёт все расчёты и итоговую заметку, затем возвращает `note_id`, массив `quote_ids` и признак `replayed`. Премия и указанная страховая сумма должны быть положительными. `sum_insured: null` допустима только для ОСАГО. Для КАСКО `official_dealer` должен быть проверенным логическим значением, а `deductible` — проверенной неотрицательной суммой в рублях; нулевая франшиза передаётся как `0.00`, отсутствие или `null` отклоняется. У остальных видов оба поля можно опустить. Точный повтор старого запроса КАСКО без этих полей по тому же ключу идемпотентности возвращает прежние ID без создания дублей. Компания и вид страхования находятся по имени без учёта регистра; если их нет, создаются новые записи справочника. Ссылка, период, платформа и статус записываются в комментарий каждого расчёта. Метод не принимает ID чужих записей, не создаёт записи в удалённой сделке и не меняет существующие расчёты. Заметки помечаются автором `Codex`; расчёты создаются без пользовательского `seller`.

Выпускайте и отзывайте ключ командой `python manage.py codex_write_key issue --name <название>` и `python manage.py codex_write_key revoke --prefix <prefix>`. Сохраняйте его через `Set-Crm3WriteCredential.ps1` из навыка `crm3-writer` в отдельном от ключа чтения каталоге Windows DPAPI. Значение ключа показывается только при выпуске и не должно попадать в репозиторий, журнал команд или сообщения. Для записи используйте `Write-Crm3.ps1`; после ответа сверяйте возвращённые ID через API чтения.

## Подготовка данных и заявки через Codex

Подготовка использует существующий **ключ записи**; новый ключ не требуется. Ключ чтения остаётся только для чтения. Поиск перед созданием человека: `GET /api/v1/codex/clients/?q=<ФИО, контакт или UUID>`. `GET /api/v1/codex/clients/<uuid>/` возвращает карточку и неудалённые паспорта/ВУ; `GET /api/v1/codex/references/?kind=insurance_companies|insurance_types|banks|platforms&q=<строка>` — справочники. Поиск постраничный; удалённые записи исключены.

Запись состоит из двух запросов:

1. `POST /api/v1/codex/write/deals/<uuid>/preparation/preview/` принимает `operations` — упорядоченный список `{ref, entity, id?, data, source}`. `source` обязателен и описывает источник значений (до 1000 символов); ссылки `@ref` в данных указывают на результат предыдущей операции. Для обновления указывается существующий `id`, для создания — только `ref`. Не более 50 операций, тело до 256 КиБ. Уникальный `ref` начинается с латинской буквы, далее допускает буквы, цифры и подчёркивание; максимум 64 символа.
2. Предпросмотр возвращает `changes` с типами `create`, `fill`, `add_links`, `replace`, список обязательных `confirmations`, `results` с ID (для заявки также версию) и `missing_fields` заявок. Он не сохраняет данные. Полученный `preview_token` нужен для `POST .../preparation/apply/` с теми же операциями и точным списком `confirmations` (`ref`, `field`, `old`, `new`, `source`); заголовок `Idempotency-Key` — UUID. Не пересылайте подтверждения автоматически, если пользователь ещё не согласовал замены.

Разрешённые сущности: `client`, `participant`, `passport`, `driver_license`, `vehicle`, `vehicle_registration`, `vehicle_title`, `mortgage`, `mortgage_balance`, `platform`, `request`. Удаление, объединение, возврат закрытой заявки в работу и изменение существующих полисов/предложений через подготовку запрещены.

Непустое существующее значение заменяется только после явного подтверждения пользователем списка старых/новых значений и источников. `false` и `0` считаются непустыми значениями. Активация нового документа, снимающая актуальность прежнего, также требует подтверждения. Дополнение списка источников без удаления прежних ссылок не заменяет существующие данные.

Подписанный токен предпросмотра привязан к ключу, сделке, операциям и исходному состоянию; срок действия — 30 минут. Если исходные данные изменились, применение отклоняется с `409`: нужно получить новый предпросмотр. Недостающие подтверждения отклоняются; записи пакета сохраняются атомарно. Повтор того же успешного запроса с тем же ключом идемпотентности возвращает прежние ID без дублей. Токен, реквизиты и полный пакет не следует выводить в технические логи.

После применения следует заново прочитать структурированные данные и паспорт заявки, сверить ID, роли и условия. Исторические снимки версий не переписываются.

Новый человек получает владельцем продавца сделки; сведения о выполненной операции записываются от имени Codex. Клиента из другой сделки сначала явно добавляют участником текущей. При совпадении VIN в сделке, номера документа у владельца или ФИО и известной даты рождения человека создание дубликата отклоняется с ID найденной записи — её нужно проверить и использовать явно. В PostgreSQL одинаковые операции создания человека по ФИО/дате рождения сериализуются advisory-блокировкой. Это не автоматическое объединение людей.

## Управление состоянием заявок и данных

Действующий ключ записи поддерживает `POST /api/v1/codex/write/deals/{deal}/lifecycle/preview/` и `/lifecycle/apply/`. Перевыпуск ключа не нужен; прежние методы совместимы.

Операция: `{ref, entity, id, action, source}`. Для `variant` нужны `action: "set_status"`, `status: "pending"|"declined"|"failed"` и `explanation` для отказа/ошибки. Для `request` доступны `close`, `reopen`, `delete`, `restore`; для `participant`, `passport`, `driver_license`, `vehicle`, `vehicle_registration`, `vehicle_title`, `mortgage`, `mortgage_balance` — `activate`, `deactivate`, `delete`, `restore`. Общие клиенты, справочники, файлы, полисы и предложения не входят в этот перечень.

Предпросмотр принимает `{operations: [...]}` (до 50 уникальных записей/ref, 256 КиБ). Возвращает `results`, `changes`, `confirmations`, `blockers`, `affected_requests`, подписанный `preview_token` на 30 минут и `committed: false`. Предпросмотр полностью откатывается. Применение принимает те же операции, токен и точный список подтверждений; обязателен UUID `Idempotency-Key`. Изменение исходных данных, повтор UUID с другим телом или блокировки дают `409`, неподтверждённая смена актуального документа — `400`. Повтор успешного тела/UUID возвращает сохранённый ответ, включая после истечения токена.

Удаление мягкое и без каскада: версии, результаты и роли сохраняются; участник исключается без удаления клиента. Использование открытой заявкой блокирует удаление/деактивацию и возвращает её ID, название и сделку. Для личных документов проверяются также другие сделки. Подтверждённая активация другого документа атомарно деактивирует прежний, а паспорт заявки выявляет изменение источников. Восстановление возвращает запись неактуальной, заявку закрытой; возврат проверяет доступность объекта и участников. Вариант должен относиться к текущей версии открытой заявки; при наличии предложений или статусе `quoted` его нельзя сбросить. Изменения записываются в `RecordHistory` с авторством Codex; исторические снимки сохраняются.

Дополнительные постраничные маршруты ключа чтения:

- `GET /api/v1/codex/deals/{deal}/records/{entity}/` — перечисленные выше сущности плюс `variant`.
- `GET .../records/{entity}/{record}/` и `.../{record}/history/` — поля и журнал записи.
- `GET .../requests/{request}/versions/` — версии и снимки заявки.

Фильтры: `deleted=exclude` (по умолчанию), `include`, `only`; `current=all` (по умолчанию), `true`, `false`. Параметры `page`/`page_size` и предел 5 МиБ действуют как прежде. Удалённые родители и историческое участие видимы при явном включении удалённых; удалённая сделка недоступна всегда. Проверка сохранения выполняется через API без браузерной сессии.

Навык управляет состоянием по поручению пользователя. Самостоятельная очистка разрешена только для доказанных неиспользуемых дублей, созданных Codex и не изменённых пользователем, с указанием сохраняемой записи. Для заявки должны совпадать роли, объект, период и условия, отсутствовать результаты. Неясное происхождение или непроверенные связи исключают автоматическую очистку.

## Работа с документами

API возвращает исходный файл размером до 25 МБ, а чтение текста PDF, сканов и фотографий выполняет Codex локально. Выбранный файл хранится во временной папке только на время ответа и затем удаляется. Методы чтения не запускают CRM-распознавание документов: оно может создавать заметки и записи истории. При ссылке на файл из другой сделки API не отдаёт его содержимое.

Вложение заметки появляется в каталоге только тогда, когда его ID подтверждён в папке сделки, клиента или полиса. Если Google Drive недоступен, файловый каталог отвечает `502`, включая случай, когда часть локальных вложений доступна: так API не выдаёт непроверенные Drive ID.

В ответе навык указывает источник каждого существенного факта: раздел и ID записи CRM либо название документа и страницу. Несовпадения между полями CRM и документами показываются отдельно, без автоматического исправления.

## Проверка и развёртывание

Backend: выполните тесты приложения `codex_reader`, `python manage.py check`, проверки форматирования и статического анализа из CI. Затем проверьте сценарий с тестовой сделкой: чтение и файлы, отказ при подмене ключей, отзыв ключа, атомарную запись предложений, повтор запроса, закрытую и удалённую сделку и отсутствие записи в чужую сделку. Навыки проверьте `quick_validate.py` и тестом клиента без рабочего ключа.

Развёртывание идёт через существующий CI. Выпуск рабочего ключа записи и пробная запись в тестовую сделку — отдельный шаг после развёртывания. Существующие данные Кусаевой не переносятся в раздел «Расчёты» задним числом.
