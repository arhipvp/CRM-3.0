# Данные и заявки страхования

Сделка объединяет работу с клиентом и может содержать несколько независимых автомобилей, ипотек, участников, заявок и полисов. Основной клиент сделки не определяет страхователя всех её полисов.

## Модель

`Client` дополнен `sex`, `birth_place`, `registration_address`. У клиента нет признака актуальности: любой неудалённый человек доступен для выбора. Актуальность участия в конкретной сделке хранится у `DealParticipant`. Дата рождения необязательна. `DealParticipant` связывает клиентов со сделками. `ClientPassport` и `DriverLicense` относятся к человеку, `VehicleRegistration` и `VehicleTitle` — к автомобилю. Документы содержат `source_links`: список `{label, url}`; разрешены HTTP(S), автоматического скачивания по ссылкам нет. Стаж, указанный только годом, сохраняется как 31 декабря этого года.

`Vehicle` и `Mortgage` принадлежат сделке. `MortgageBalance` хранит отдельные значения остатка долга и даты. `is_current` отделён от `deleted_at`: мягко удалённые и неактуальные записи сохраняют историю. Для каждого человека/автомобиля допускается единственный актуальный живой документ соответствующего типа.

`InsuranceRequest` ссылается ровно на один автомобиль или ипотеку, вид страхования, участников с ролями и обязательные пары страховщик/платформа. КАСКО содержит список франшиз, признак официального дилера и режим фиксированной/максимальной стоимости. Ипотечная заявка фиксирует банк, сумму и дату задолженности. `RequestVersion` сохраняет снимок условий, `RequestVariant` — результат работы по компании, платформе и франшизе. Старые варианты и предложения не заменяются новой версией. Закрытую заявку перед редактированием возвращают в работу.

Расчёты и полисы сохраняют существующие разделы и необязательную связь с заявкой. Расчёт связан также с вариантом и версией, фактические сумма и условия хранятся у предложения. Старые записи из текстов автоматически не преобразуются.

## Codex

Обычный JWT API использует префикс `/api/v1/insurance-data/`: `participants`, `passports`, `driver-licenses`, `vehicles`, `vehicle-registrations`, `vehicle-titles`, `mortgages`, `mortgage-balances`, `platforms`, `requests`, `variants`. Списки фильтруются по доступным связям (`deal`, `client`, `vehicle`, `mortgage`, `insurance_request`), `is_current`, `include_deleted=true`. Мягкое удаление — `DELETE`, восстановление — `POST <id>/restore/`, история — `GET <id>/history/`. У заявок также есть `close/`, `reopen/`, `copy/`, `passport/`. Варианты создаются из матрицы заявки, их статус/пояснение меняются через `PATCH`.

Список клиентов поддерживает `show_deleted=true`, восстановление клиента — `POST /api/v1/clients/<id>/restore/` для владельца или администратора. Компактный поиск клиентов предлагает все неудалённые карточки.

- `GET /api/v1/codex/deals/<uuid>/data/` возвращает структурированные данные сделки и список заявок.
- `GET /api/v1/codex/deals/<uuid>/requests/<request_uuid>/passport/` возвращает снимок текущей версии заявки, варианты, расчёты и полисы. `?version=<id>` выбирает **целочисленный ID RequestVersion**, не порядковый номер версии.
- Оба метода используют существующий ключ чтения, исключают удалённые сделки, ограничивают JSON 5 МиБ (`413`). Существующий паспорт сделки версии 1 не меняется.
- В предложении API записи необязательные `request_variant` (UUID) и `request_version` (ID) передаются вместе. Проверяются сделка, актуальная версия, страховщик, вид страхования и соответствие условий. Ключ записи по-прежнему разрешает только создание предложений и заметок. Старые запросы и их идемпотентные повторы сохраняют поведение.

## Объединение людей

Предпросмотр объединения клиентов возвращает `document_conflicts` для нескольких актуальных паспортов или ВУ. Для каждого конфликта пользователь выбирает документ через `field_overrides.current_passport_id` / `current_driver_license_id`. Выбор проверяется до переноса Drive и повторно при финализации в транзакции. Выбранные ID сохраняются в сессии объединения; чужие и устаревшие документы отклоняются.

Все документы, включая удалённые, переносятся целевому клиенту; остальные актуальные документы становятся неактуальными. Участия в сделке объединяются без дублирования, роли заявок и водители переводятся на целевого клиента. Исторические JSON-снимки версий не переписываются. `Policy.client` меняется только при ссылке на объединяемого человека, а не у всех полисов его сделок.

Объединение сделок переносит автомобили, ипотеки и заявки вместе с существующими полисами/расчётами. Участники объединяются без живых дублей, неактуальные и удалённые связи сохраняют состояние (при включённом переносе удалённых). Документы объектов и варианты продолжают ссылаться на те же объекты. Снимок версии хранит первоначальные идентификаторы сделки/людей: после объединения источники считаются изменёнными, перед новым расчётом заявку необходимо проверить и сохранить новой версией.

Если в сделках есть участники или другие структурированные записи, объединение требует `include_deleted=true` (значение по умолчанию). Запрос с `false` отклоняется до операций Drive: иначе удалённый объект или участник мог бы остаться в старой сделке при переносе ссылающейся на него заявки.

## Совместимость и выпуск

Сначала применяются миграции и backend, затем frontend. Миграции создаются Django; поле актуальности клиента удаляется отдельной миграцией без изменения остальных данных и исторических снимков; основной клиент и страхователи полисов добавляются как участники. Новые заявки и объекты по старому тексту не угадываются. Production-развёртывание выполняется отдельным шагом.
